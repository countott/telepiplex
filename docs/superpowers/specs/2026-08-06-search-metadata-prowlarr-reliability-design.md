# Search 元数据与 Prowlarr 可靠性集中修复设计

**日期：** 2026-08-06  
**状态：** 已完成规则确认和设计自检，等待用户复核  
**涉及范围：** Host、Search Feature、Rename Feature  

## 1. 背景

当前 Search、Host 和 Rename 已经具备候选搜索、固定链接读取、元数据补全、增量 Prowlarr 搜索、下载交接和文件树反查能力，但五处边界没有形成一致的用户流程：

1. 普通搜索只有一个候选时会自动进入 Prowlarr，媒体确认内容与任务状态共用一条消息，随后被进度覆盖。
2. Prowlarr 增量搜索已经生成可选序号，但 Host 只允许 `awaiting_input` 状态下的 Feature 回调，导致运行中按钮被拦截。
3. Prowlarr 结果虽然紧凑，但标题、搜索器统计、规格和种子状态的层次仍不符合最终产品文案。
4. `/m` 下载后的文件树反查只调用 `media.search.resolve_metadata` 的无交互分支；同类型候选不止一个时直接失败，没有进入可恢复确认。
5. 豆瓣适配器在稀疏接口返回有效事实后立即停止，没有继续合并富接口中的海报、国家、原名和别名。

真实查询验证进一步表明：

- `繁花 2023`、`倚天屠龙记 2019`可形成唯一中文名和年份硬匹配。
- `Dune 2021`、`Oldboy 2003`在稀疏事实下无法硬匹配；富接口实际提供了可用英文名或别名。
- `The Office US 2005`不能稳定依赖一次文本查询唯一定位，应进入人工确认。
- 豆瓣电影直链可能因稀疏事实缺少规范拉丁标题而无法形成严格元数据。

本设计把五项修复作为一个协调批次处理，共用一套身份锁定、元数据补全、独立确认消息和端到端回归规则。

## 2. 目标

本批必须达到以下结果：

- `/s`、直接元数据链接和 `/m` 文件树反查在身份锁定后复用同一套元数据补全逻辑。
- 直链和可信的 `/m` 唯一匹配不增加无意义的候选点击。
- 低置信度 `/m` 反查可暂停、确认并恢复原 Rename 任务。
- 每次最终身份确认都生成一条不会被任务进度覆盖的独立消息。
- 首次豆瓣候选能够显示海报、国家或地区、年份和媒体类型。
- Prowlarr 搜索运行期间已出现的序号可以立即选择。
- Prowlarr 文案遵守已确认的极简层级和种子状态规则。
- 所有新状态均可幂等重试，并通过进程恢复保持一致。

## 3. 非目标

- 本批不设计或扩展音轨呈现。语言、编码、声道、对象音频和多音轨层级留给后续独立迭代。
- 本批不改变 Prowlarr 片源硬门禁、下载提供方、115 投递或 Plex 交接规则。
- 本批不允许 AI 直接生成、重写或覆盖最终媒体身份。
- 本批不把完整文件树拼入搜索文本。
- 本批不改变 `/s` 仅接受片名的命令合同；支持的元数据链接仍通过直接消息进入 Search。

## 4. 总体架构

### 4.1 三条入口，共用一个补全阶段

三条入口保持各自的发现方式：

```text
/s 片名
  -> 豆瓣候选发现
  -> 唯一硬匹配自动锁定，或用户选择
  -> 统一元数据补全

直接元数据链接
  -> 稳定 ID 精确读取并锁定
  -> 统一元数据补全

/m 磁力链
  -> 下载完成
  -> Rename 从资源名和文件树构建结构化探针
  -> Search 唯一硬匹配自动锁定，或返回待确认候选
  -> 统一元数据补全
```

统一补全阶段负责：

1. 精确读取已冻结来源；
2. 合并豆瓣稀疏和富事实；
3. 补充 Wikipedia；
4. 对剧集补充 TVDB 根条目和季集库存；
5. 应用电影、全剧、指定季或指定集范围；
6. 生成并确认严格 `media_metadata v1`；
7. 生成统一的身份展示数据。

### 4.2 身份锚点不可漂移

- 直链的稳定 ID 是强锚点，不经过普通候选发现。
- `/s` 或 `/m` 选择的豆瓣 subject ID 在进入补全阶段后冻结。
- 补充来源只能增加字段或验证关系，不能改变已冻结作品。
- 稳定 ID、年份或媒体类型发生冲突时停止自动路径，不能静默覆盖。
- AI只允许改写查询或形成候选短名单，不能创建元数据事实。

## 5. 豆瓣事实合并

### 5.1 读取规则

同一 subject ID 的读取不再在第一个有效接口处短路。适配器读取：

1. `subject_abstract` 稀疏接口；
2. `rexxar` 富接口。

只要任一接口返回同一 subject ID 的有效事实，就保留该事实；两者都成功时执行确定性合并。只有两者均不能形成有效事实时，才返回来源失败或未找到。

缓存存储合并后的事实，避免后续固定链接补全再次得到稀疏版本。

### 5.2 字段规则

合并后的豆瓣事实至少保留：

- `subject_id` 和固定 URL；
- 中文名；
- 英文名、官方英文名、原名和别名；
- 年份；
- 电影或剧集类型；
- 国家或地区；
- 类型标签；
- 海报；
- 简介；
- 原始语言。

合并原则：

- 稳定 ID 必须一致。
- 富接口补充稀疏接口为空的字段。
- 列表字段去空、去重并保序。
- 稀疏和富接口的非空年份或媒体类型冲突时，事实不可用于自动确认。
- `countries` 必须进入标准事实、候选预览和最终身份展示。
- 海报优先使用已冻结锚点来源的有效 HTTPS 图片。

## 6. 普通 `/s` 与直链

### 6.1 普通 `/s`

- 首轮继续使用豆瓣发现。
- 标题或权威别名、年份和媒体类型形成唯一硬匹配时，可以自动锁定。
- 两到五个可选候选时展示候选列表。
- 初次候选必须显示海报、规范片名、年份、国家或地区以及电影或剧集类型。
- 唯一自动匹配不再要求额外点击，但仍必须在补全和范围确认后发送独立身份消息。

### 6.2 直链

- 豆瓣、Wikipedia 和 TVDB 的稳定实体链接直接精确读取。
- 直链不展示普通候选列表。
- 精确读取完成后直接进入统一补全阶段。
- 锚点读取失败时返回固定链接读取失败和重试入口，不降级到可能改变作品身份的模糊搜索。
- 可解析分享页如果最终能得到稳定实体链接，按直链处理；只能得到纯标题时才按现有降级规则重新开始普通标题搜索。

## 7. `/m` 文件树反查与 Rename 恢复

### 7.1 探针构建

Rename 从下载事件构建独立字段：

- `identity_query`；
- `year_hint`；
- `content_shape`；
- `observed_seasons`；
- `observed_episodes`；
- `video_count`。

年份必须从完整顶层资源名中先提取，再删除 `S01`、`E01`、分辨率、编码、来源和质量标记。文件树只用于推断内容形态和季集范围，不与片名拼成一句搜索文本。

### 7.2 自动锁定条件

`/m` 只有同时满足以下条件才自动锁定：

- 标题或权威别名严格匹配；
- 年份严格匹配；
- 探针推断的电影或剧集类型匹配；
- 最终只有一个候选满足所有条件。

年份缺失、同类型同年份候选不唯一、来源事实冲突或查询质量不足时，禁止自动选择。

### 7.3 Capability 返回合同

`media.search` 保留 `resolve_metadata`，但把普通歧义从异常改成结构化结果：

```text
resolved
  media_metadata
  naming_metadata
  presentation

confirmation_required
  query
  probe
  candidates[1..5]

unresolved
  reason_code
```

`confirmation_required` 中每个候选只携带可展示字段和稳定候选引用。稳定候选引用必须能够在进程重启后重新精确读取，不能依赖 Search 内存中的临时下标。

Search 增加确认方法，接收稳定候选引用和原探针，重新精确读取该候选并进入统一补全阶段。

### 7.4 Rename 状态

收到 `resolved` 时，Rename：

1. 持久化严格元数据；
2. 发送独立身份消息；
3. 继续原组织任务。

收到 `confirmation_required` 时，Rename：

1. 将 durable job 标记为等待元数据确认；
2. 持久化查询、探针和稳定候选引用；
3. 把 operation 转为 `awaiting_input`；
4. 使用 `rename` 回调命名空间展示候选；
5. 用户选择后调用 Search 确认方法；
6. 持久化返回元数据，发送独立身份消息并恢复同一个 job。

该路径不重新下载、不进入 Prowlarr。用户退出时不得删除下载内容；按既有未整理目录策略保存。

进程恢复时，等待确认的 job 必须恢复同一候选键盘；已确认但尚未组织的 job 必须从持久化元数据继续，不能重复搜索或重复发送身份消息。

## 8. 独立身份消息

### 8.1 Host milestone

Host 提供与 operation 状态消息分离的幂等 milestone 通道。Feature 只能对自己当前拥有的 operation 发布 milestone，Host 根据 operation 记录确定聊天和用户，Feature 不能自行指定任意聊天目标。

milestone 使用 `(operation_id, milestone_id)` 幂等。身份消息的 milestone ID由已确认媒体身份和范围稳定生成。重复回调、重试或进程恢复不得重复发送。

milestone 不写入 operation 的 `message_id`，后续 Prowlarr、Rename 或下载进度不会编辑它。

### 8.2 展示规则

身份消息在身份和最终范围确定后发送，内容包含：

- 海报；
- `中文名 (规范英文名)`；
- 年份；
- 国家或地区；
- 电影或剧集类型；
- 全剧、指定季或指定集；
- 已验证来源。

命名降级顺序：

1. 中文名和规范英文名都存在且规范化后不同：`中文名 (规范英文名)`；
2. 只有中文名：中文名；
3. 中文名缺失：规范英文名。

自动确认的消息不带确认按钮。海报不可发送时降级为同内容文本。

Search 在进入 Prowlarr 前发送该 milestone；Rename 在写入严格元数据、开始存储变更前发送该 milestone。

## 9. Prowlarr 运行中选择

### 9.1 Host 门禁

Host 不全面开放 `running` 状态回调。只有 operation 同时满足以下条件时才允许：

- `state == running`；
- Feature 在 operation details 中显式声明运行中交互；
- 当前 stage 为 `prowlarr_search`；
- callback 出现在当前 operation 键盘；
- callback 消息 ID与 operation 当前消息 ID一致；
- callback 命名空间属于当前 Feature。

其他运行中回调继续返回“当前任务执行中”。

### 9.2 Search 冻结

用户在增量搜索中点击已出现序号时：

1. Telegram callback 立即响应；
2. Search 原子设置 `selection_frozen` 和选中 release ID；
3. 取消总搜索任务和未完成搜索器任务；
4. 后续完成回调不得覆盖状态；
5. 进入片源解析和下载投递。

重复点击、过期按钮或已经消失的片源只返回状态已变化，不得二次投递。

## 10. Prowlarr 文案

### 10.1 标题与统计

搜索中：

```text
🔍 繁花 (Blossoms Shanghai)
搜索器 3/5，离线 1
```

搜索完成：

```text
✅ 繁花 (Blossoms Shanghai)
搜索器 5/5，离线 1
```

标题不使用警告 Emoji。部分搜索器离线、全部离线或无结果都通过统计和正文表达。

统计定义：

- 总搜索器数为 `m`；
- 离线搜索器数为 `x`；
- 分母为可用搜索器数 `m - x`；
- 分子为已经成功完成的可用搜索器数 `n`；
- 固定显示 `搜索器 n/(m-x)，离线 x`；
- 不显示可用结果数、过滤数、异常数或搜索器名称。

### 10.2 结果结构

每个结果固定两行：

```text
① 2160p · WEB-DL · x265 · DV
   58.4 GB｜活种
```

规则：

- 最多显示十二个去重版本。
- 序号按钮与正文序号严格对应，每行最多三个。
- 第一行只显示范围、分辨率、来源、视频编码、动态范围和版本标签。
- 第二行只显示大小和种子状态。
- 不显示原始做种数、发布组、搜索器名称或内部评分。
- 原始发布名只在规格无法解析且必须区分两个结果时，以受限长度降级显示。
- `4K`、`UHD` 和 `2160p`统一显示为 `2160p`。
- `HEVC`、`H.265` 和 `x265`统一显示为 `x265`。
- `AVC`、`H.264` 和 `x264`统一显示为 `x264`。
- 同一规格标签不得重复。
- 本批新版文案不展示音轨标签。

### 10.3 种子状态

适配器必须区分“明确为零”和“未提供”，不能再使用 `value or 0`合并两者。

同一 infohash 被多个搜索器返回时，合并各来源的显式 seeders 统计并取最大值，再判断：

- 最大显式值大于等于 3：`活种`；
- 最大显式值为 1 或 2：`疑似死种`；
- 所有显式值均为 0：`死种`；
- 没有任何可解析的显式值：`疑似死种`。

这是 Prowlarr 统计风险标签，不宣称执行了实时 Tracker 或 DHT 验证。现有排序仍可使用数值统计，但用户文案只展示三态标签。

## 11. 错误处理

- 豆瓣一个端点失败、另一个端点成功时使用可用事实并记录来源降级。
- 豆瓣两个端点都失败时返回结构化来源失败。
- 直链锚点读取失败不得改变身份。
- `/m` 歧义不是终态错误，必须进入可恢复确认。
- `/m` 未找到候选时不得开始存储改名。
- 身份 milestone 发送失败时降级文本；元数据本身有效时不因此回滚身份确认。
- Prowlarr 部分搜索器离线不阻止其他搜索器结果选择。
- 用户选择结果后，任何迟到搜索器结果都不得恢复旧键盘或覆盖新阶段。

## 12. 测试策略

### 12.1 豆瓣适配器

- 稀疏和富接口成功时合并字段。
- 只有一个接口成功时确定性降级。
- ID、年份或媒体类型冲突时拒绝自动事实。
- 国家、海报、英文名、原名和别名进入标准事实。
- `Dune 2021`和`Oldboy 2003`可通过富事实形成英文别名硬匹配。

### 12.2 Search

- 普通 `/s` 唯一匹配自动补全并发送 milestone。
- 多候选仍显示海报、国家、年份和媒体类型。
- 豆瓣直链跳过候选并补齐规范拉丁标题。
- 直链锚点失败不降级到其他作品。
- `resolve_metadata` 唯一匹配返回 `resolved`。
- 同类型歧义返回 `confirmation_required`，不抛终态异常。
- 稳定候选引用可在新 Search 实例中重新确认。
- Prowlarr 运行中选择冻结结果并取消所有剩余任务。
- 迟到结果和重复点击不会二次投递。

### 12.3 Rename

- 年份在删除季集标记前提取。
- `/m` 唯一匹配发送 milestone 后继续组织。
- `/m` 歧义持久化等待状态并展示候选。
- 选择候选后恢复同一个 durable job。
- 进程恢复不会重复元数据查询或 milestone。
- 用户退出保留内容并进入既有未整理兜底。

### 12.4 Host

- milestone 与 operation 状态消息分离。
- milestone 幂等且只能由当前 owner 发布。
- `running` 回调默认继续被拒绝。
- 显式运行中交互只允许当前 stage、当前消息和当前键盘中的 callback。

### 12.5 Prowlarr 文案

- 标题使用 `🔍/✅ + 中文名 (规范英文名)`。
- 统计只显示 `搜索器 n/(m-x)，离线 x`。
- 完成时只改变 Emoji。
- `2160p`、`x265`、`x264`归一化符合规则。
- 结果不显示原始 seeders、发布组和搜索器名称。
- `>=3`、`1..2`、`0`、缺失四种输入映射到正确状态。
- 多来源同 infohash 取最大显式 seeders。
- 新版文案不显示音轨标签。

### 12.6 回归

先运行相关 Host、Search 和 Rename 测试，再运行 Core 及五个 Feature 的完整本地测试。所有验证均禁用字节码和 pytest 缓存。Mac 本地不执行任何 Git 操作。

## 13. 实施顺序

该设计作为一个集中修复批次交付，但实现和验证按依赖顺序拆分：

1. 豆瓣双端点事实合并和候选字段；
2. 统一身份展示和 Host milestone；
3. `/s`、直链的独立身份消息；
4. `/m` 唯一确认、歧义合同和 Rename durable 恢复；
5. Host 运行中回调门禁；
6. Prowlarr 文案、种子状态和运行中选择；
7. 跨模块回归和完整本地测试。

每一步先写失败测试，只修改该边界，再运行相关回归；最后统一运行全量测试。
